# API Gateway deployment

`openapi.json` in this folder defines the entire REST API — all 30 resource
paths, every method, CORS preflight, and the Cognito authorizer — as one
OpenAPI 3.0 document. Importing it is a single AWS CLI call instead of
manually clicking through ~30 resources in the console. It's a hand-written,
one-off file (not generated by a script) — if routes change later, edit it
directly, or ask for the relevant section to be regenerated.

## Why these specific choices

Read directly from this repo's own code (`app/lib/params.py`), not from
inspecting any AWS account:

- **Must be a REST API (API Gateway v1), not an HTTP API (v2).** `Params`
  reads the user id from `requestContext.authorizer.claims.sub` — that
  exact shape is only produced by a REST API with a Cognito User Pool
  authorizer.
- **Must use named resource paths, not a `{proxy+}` catch-all.** `Params`
  reads path params by name from `event["pathParameters"]` (e.g.
  `account_id`). A catch-all proxy resource only gives API Gateway a single
  generic `proxy` key — every route needing a path param would break.
- **OPTIONS needs its own mock integration per path.** The app's own router
  has no OPTIONS handler; `openapi.json` already includes a CORS mock
  response on every path (mirrors `AWSLambdaResponse.generate()`'s existing
  `Access-Control-Allow-*` headers in `app/lib/response.py` exactly).

## Prerequisites

- The Lambda function already deployed (`scripts/deploy/lambda.sh`).
- Its **invocation ARN**: `arn:aws:apigateway:<region>:lambda:path/2015-03-31/functions/<lambda-function-arn>/invocations`
- Your **Cognito User Pool ARN**: `arn:aws:cognito-idp:<region>:<account-id>:userpool/<pool-id>`
- AWS CLI configured with the `dompet-user` profile (same one `Setup.py` uses).

## Steps

1. **Fill in the two placeholders** in `openapi.json` (find and replace):
   - `__LAMBDA_INVOKE_ARN__` → your Lambda's invocation ARN above
   - `__COGNITO_USER_POOL_ARN__` → your Cognito User Pool ARN

2. **First-time only — create the REST API:**
   ```bash
   aws apigateway import-rest-api \
     --profile dompet-user \
     --region <region> \
     --body fileb://scripts/deploy/openapi.json
   ```
   Note the returned `id` (the REST API ID) — you'll need it for every future update.

3. **Updating an existing REST API** (after editing `openapi.json`):
   ```bash
   aws apigateway put-rest-api \
     --profile dompet-user \
     --region <region> \
     --rest-api-id <rest-api-id> \
     --mode overwrite \
     --body fileb://scripts/deploy/openapi.json
   ```

4. **Let API Gateway invoke the Lambda** (one-time, per REST API — this is
   a separate permission from the authorizer/IAM role the Lambda itself
   runs as):
   ```bash
   aws lambda add-permission \
     --profile dompet-user \
     --region <region> \
     --function-name dompet \
     --statement-id apigateway-invoke \
     --action lambda:InvokeFunction \
     --principal apigateway.amazonaws.com \
     --source-arn "arn:aws:execute-api:<region>:<account-id>:<rest-api-id>/*/*/*"
   ```

5. **Deploy a stage** (nothing is live until this runs):
   ```bash
   aws apigateway create-deployment \
     --profile dompet-user \
     --region <region> \
     --rest-api-id <rest-api-id> \
     --stage-name prod
   ```
   Re-run this same command after every `put-rest-api` update — importing/overwriting
   the definition does not itself redeploy the live stage.

6. **Test:**
   ```bash
   curl -H "Authorization: <cognito-id-token>" \
     https://<rest-api-id>.execute-api.<region>.amazonaws.com/prod/accounts
   ```

## Manual setup via the AWS Console (no CLI import)

If `dompet-user` doesn't have the API Gateway CLI permissions needed for
`put-rest-api`/`import-rest-api` and you don't want to change that, the
same result can be built by hand in the console. It's the same ~52
method configurations either way; this just does it through clicking
instead of one file upload.

### One-time setup

1. **Authorizer**: your REST API → **Authorizers** → **Create New Authorizer**
   → Type: **Cognito** → select your User Pool → Token Source: `Authorization`.

### Per resource path (repeat for all 30 rows below)

1. **Actions → Create Resource.** For a path segment in `{curly braces}`
   (e.g. `{account_id}`), type it exactly like that as the resource path —
   the console treats `{name}` as a path parameter automatically, same as
   the OpenAPI spec does.
2. **For each method** listed for that path: **Actions → Create Method** →
   pick GET/POST/PUT/DELETE → Integration type **Lambda Function** → check
   **Use Lambda Proxy integration** → Lambda function: `dompet` (same
   region) → Save. The console will prompt to add Lambda's resource
   policy permission automatically the first time — accept it (this
   replaces the CLI's `lambda add-permission` step, and only needs
   granting once per REST API, not once per method).
3. **Method Request** (for each method) → **Authorization** → select the
   Cognito authorizer created above.
4. **After all of that resource's methods are added**: **Actions → Enable
   CORS** → accept the defaults, or set Access-Control-Allow-Headers to
   `Content-Type,Authorization` to match `app/lib/response.py`'s existing
   CORS headers exactly. Re-run this any time you add another method to
   an already-CORS-enabled resource, since it needs to know about every
   method to list them in `Access-Control-Allow-Methods`.

```
/accounts/{account_id}/reactivate                            POST
/attachments                                                 GET POST
/attachments/{attachment_id}                            DELETE GET PUT
/budgets                                                     GET POST
/budgets/{budget_id}                                    DELETE GET PUT
/budgets/{budget_id}/members                                 GET POST
/budgets/{budget_id}/members/{member_user_id}                    DELETE
/budgets/{budget_id}/transactions                            GET
/categories                                                  GET POST
/categories/{category_id}                                DELETE PUT
/locations                                                   GET POST
/locations/{location_id}                                DELETE GET PUT
/tags                                                        GET POST

/transactions                                                GET POST
/transactions/search                                         GET
/transactions/{transaction_id}                               GET PUT
/transactions/{transaction_id}/attachments                   GET POST
/transactions/{transaction_id}/attachments/{attachment_id}       DELETE
/transactions/{transaction_id}/budgets                       GET POST
/transactions/{transaction_id}/budgets/{budget_id}               DELETE
/transactions/{transaction_id}/deactivate                    POST
/transactions/{transaction_id}/reactivate                    POST
/transactions/{transaction_id}/rollback                      POST
/transactions/{transaction_id}/tags                          GET POST
/transactions/{transaction_id}/tags/{tag_id}                     DELETE
```

A path like `/accounts/{account_id}/locations` needs its parent
(`/accounts/{account_id}`) created first — the console requires building
the resource tree top-down, same as the path structure implies.

`/transactions/search` is the one case where a literal child resource
(`search`) sits alongside a `{transaction_id}` parameter resource under
the same parent (`/transactions`) — API Gateway supports both existing
as siblings and matches the literal one first for an exact `/transactions/search`
request, same as the app's own route matching already does (`search` never
matches the UUID-shaped `{transaction_id}` pattern).

### Deploy

**Actions → Deploy API** → Deployment stage: `staging` (existing) →
Deploy. Repeat this after every batch of changes — nothing is live until
a deployment is made, same as the CLI's `create-deployment` step.

## Not covered here

- Custom domain name / ACM certificate — set up separately if wanted, unrelated to this file.
- Throttling, usage plans, WAF — none configured; add later if needed.
- The Cognito User Pool itself, and the `dompet-user` IAM permissions needed to run these commands — assumed to already exist.
